# 产物链设计经验

material CLI 的产物链:01 收集 → 02 分组 → 03 初稿 → 04 定稿,四个命令对应四个阶段。

## 1. 一个命令一个阶段一个产物

```
01 收集 ──> 02 分组 ──> 03 初稿 ──> 04 定稿
collect    organize    distill     express
```

- 命令名即阶段名,没有多余的子命令层级;`collect`/`organize`/`distill`/`express` 直接对应产物编号。
- 产物编号稳定,归档(`01-journal-收集.md` 等)、文档、讨论都引用同一套编号,避免"旧 03/新 02"这类编号漂移。
- **教训**:开发中产物编号反复调整(03+04 合并、05 重编号),每次调整都伴随理解偏差。编号与阶段应在设计阶段一次性定稿,改动需显式记录。

## 2. 中间产物必须真实存在

organize 早期版本只把主题归属写进日志 YAML,没有生成独立产物——distill 自己重新聚合,结果**分组形同虚设**:环节存在,但没有承载它的文件。

修复:organize 生成 `groups/<主题>.md`(条目原文 + 来源引用),distill 只消费分组产物,不再自己聚合。

**原则**:一个阶段如果没有独立产物,它就是多余的;有了独立产物,上下游依赖才真实(03 依赖 02、04 依赖 03,由文件缺失错误信息天然保证顺序)。

## 3. 质量问题的根因往往在上游

定稿质量连续两轮"不如第一版",前两轮都在改定稿的 prompt,效果不佳。真正根因在**初稿**:03 只是素材的线性顺述(流水账),没有立意、没有结构;04 基于这样的底稿,再怎么重构也难超越直接基于素材自由创作的第一版。

修复:升级 03 的"统一表达"为"成文"(见 [llm-prompting.md](llm-prompting.md#3-成文而非顺述)),04 未改 prompt 即自动对齐第一版质量。

**原则**:链式流水线中,下游质量的上限由上游决定。质量不达标时,先检查上游产物的质量,再考虑下游 prompt——不要在下游打补丁。

## 4. 初稿必须有用

"初稿没有什么实际作用?"——当定稿直接基于素材创作时,初稿就成了多余中间产物。初稿的价值在于它是**定稿的底稿**:提供内容骨架与统一基调,定稿在其上按目标重构。

要让初稿有用,它必须:
- **信息完整**(过滤只去杂质,不削减信息)
- **真正成文**(立意、结构、节奏,可独立阅读)
- 否则定稿会被初稿的缺陷(信息缺失或结构松散)拖累。

## 5. 标注 = 编辑元数据,整理 = 操作文件

- **标注**(主题归属、来源引用)写入 markdown 的 YAML front matter:人工可以直接用文本编辑器修改,git 天然管理历史,无需专门的 UI。
- **整理**(分组、聚合、成稿)通过文件操作完成:`groups/`、`materials/` 都是普通 markdown 文件。
- 编辑对象是 git 管理的 markdown 文档——命令只做增量修改(日志 append-only、front matter 定点更新),不破坏历史。

## 6. 产物可回溯

每个产物都携带来源引用链:分组文件的 `sources` 指向日志条目(`journal/2026-08-15.md#09-30`),初稿沿用分组的 sources,定稿可追溯到原始素材。任何成品都能回溯到最初的想法——这是素材管线的可信基础。
