# 工程实践与踩坑

## 1. HTTP 客户端不读环境代理(必踩)

**症状**:`collect --url` 下载 GitHub 文件无限挂起,直到超时被杀;而同一环境里 `curl` 0.6 秒完成。

**根因**:环境配置了代理(`HTTPS_PROXY=http://127.0.0.1:7897`);curl 自动读环境代理,而 **ureq 默认不读代理环境变量**,程序直连 GitHub 被墙挂起。

**排查方向**:curl 正常而程序超时 → 先查代理。`env | grep -i proxy` 看环境,再看 HTTP 库是否支持环境代理。

**修复**:构建 agent 时读取 `https_proxy`/`HTTPS_PROXY`/`http_proxy`/`HTTP_PROXY`/`all_proxy`/`ALL_PROXY`(仅接受 http(s) 代理,忽略 socks),并设置连接超时(15s)与总超时(120s)——即使没有代理,超时也保证不挂死。

## 2. LLM 调用无超时,长链路分步执行

- quanttide-agent 的 `LLM::complete` 无超时配置(STATUS.md 已知问题:"60s 以上请求可能挂死")。
- 四个命令串行执行时,多次 LLM 调用累计耗时可能超过单次命令的超时上限,整条命令被 kill,且**部分产物已写入、部分未写入**,状态不一致。
- **实践**:长链路用 `timeout` 逐命令执行(collect 60s / organize 120s / distill 180s / express 180s),每步验证产物再继续;不要一条命令跑完四步。
- 被 kill 后先检查已生成的产物(文件在不在),不要盲目重跑开头(重跑 collect 会追加重复条目)。

## 3. 临时目录的幻觉

- `/tmp` 下的文件可能被环境清理(下载的素材、跨调用传递的状态文件都丢过),导致"collect 成功但 organize 找不到文件"的假象。
- **实践**:跨调用的临时数据放在工作区内(`.demo-tmp/`),用完删除;关键状态(如提取出的主题名)写入文件而非依赖环境变量传递。
- 诊断"文件消失"时,先验证是写入失败还是被清理:写入后立即 `ls` 确认,再跨调用确认。

## 4. 幂等设计

- **分组幂等重建**:`write_groups` 每次按最新 YAML 全量重建 `groups/`,人工改 YAML 后重跑 organize 即刷新,不会残留旧分组。
- **标题即 id**:日志条目 id 直接由标题生成(`## 09:30` → `09-30`),同分钟多条标题带序号(`## 09:30-2`);**删除中间条目不会导致其他条目 id 漂移**(对比"按出现次数计数"的方案,后者删除条目后序号重排,YAML 标注全部错位)。
- **append-only 收集**:collect 只追加、不改写已有内容,git 历史干净。

## 5. 依赖最少化,手写受控子集

- front matter 解析器手写 ~70 行,零 YAML 依赖:领域内 front matter 由工具自己生成、格式受控,只需 `topic`/`topics`/`sources` 三个键;完整 YAML 的复杂度(锚点、类型推断)没有用武之地,反而让"人工编辑标注"变难。
- parse/render 对称设计,round-trip 测试保证"解析 → 修改 → 渲染"无损。
- 依赖清单:clap(命令解析)、chrono(时间戳)、quanttide-agent(LLM)、ureq(下载)——每个都有不可替代的用途。

## 6. 领域命名先查隐喻与模型的同构性

`Writing` 聚合根的命名决策链:Article ✗ → Document ✗ → Work △ → **Writing ✓**。

- **Article 不合适**:实验室里已用作"分析基本单位",且与 Book 是并列形态而非统摄概念。
- **Document 属于文档云**:产品线里文档云的基本单位是 Document,写作云需要自己的定义。
- **Work 是完成模型**:隐喻是"劳动的结晶"——"a work"默认已完成,素材(material)阶段的碎片在语义上断裂。
- **Writing 是过程模型**:隐喻是"行为的痕迹"——素材、便签、草稿皆是 writing,与线性状态机(material → outline → draft → final)同构。

**原则**:状态机是过程模型还是完成模型,决定了承载它的概念该用哪个词;命名不只是风格偏好,是模型语义的显式化。

## 7. 文本质量必须实测对比,不能靠感觉

三轮定稿优化,每轮的真实依据是**与第一版的逐维度对比表**(开篇/视角/结构/品牌融合/节奏/结尾):

- 第一版(直接基于素材自由生成):叙事线、读者视角、品牌升华——为什么好要拆成可对比的维度
- 每一版产物归档(`04-express-定稿.md`),git 历史即质量演进记录

**实践**:prompt 改动后必须跑真实链路(真实 API Key + 真实素材),归档产物,逐维度对比,再决定下一轮改哪里。用户说"还是不如第一版"时,对比表能快速定位差距维度(当时是结构:信息清单 vs 叙事线),而不是盲目再调 prompt。
