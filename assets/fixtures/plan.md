# 叙事风格迁移方案

## 场景

主营业务：数据处理服务、技术课程服务。

### 核心困境（迁移的锚点）

创新业务，不好和客户介绍。

这是所有迁移的出发点。原文章的张力和价值来自"创始人面对认知困境的挣扎"，业务的对应物就是这一句。以下所有迁移不替换主题，而是**用同一种叙事动作去处理不同的困境素材**。

### 困境映射

| 原始困境 | 叙事动作 | 业务困境 |
|----------|----------|----------|
| a1: 陷入具体场景，不知道自己在做什么 | 跨界找实验室 → 建模 → 验证 | 创新业务无法用现有分类讲清楚，需要先给自己建模 |
| a2: 抽象使用"认知基础设施"却不理解 | 实践突破让概念落地 | 自己的业务自己最清楚，但讲出去客户听不懂 |
| a3: 羞耻感阻止我接受客户视角 | 对话中被打开 → 重新定义 | 不好意思承认业务还没完全定型，怕显得不专业 |
| a4: 拒绝各种消耗 | 平行例示范拒绝 | 拒绝"标准化"，拒绝"对标竞品"，拒绝"等想清楚了再推" |
| a5: 环境信任下降 | 推演一个社会结构 | 客户被各种"AI/大数据"忽悠过，信任重建的困境 |

### 叙事引擎

不变的是"一个人/团队如何从说不清到说清"的认知推演动作。变的只是素材来源：
- 原始素材来源：创始人的个人经历（打游戏、交友、写小说）
- 业务素材来源：项目交付中的摩擦、客户的原话、团队内部复盘

## 样文

我们自己是搞研究出身的。

那几年攒了很多数据清洗和整理的经验。工商数据、专利数据、投融资数据，不同渠道来的，格式不统一，全自己手工对过。同样的坑踩了无数次之后，慢慢磨出了一套自己的处理流程。

后来转型做了商业公司，开始对外接项目。发现来找我们的人，很多也是做研究的——经济学、社会学、公共管理——他们的处境我们太熟悉了。手上有一堆数据，想做分析、跑模型，但七八成的时间花在了数据处理上，真正的研究没怎么动。

我们没多想，就把自己那套流程拿出来用。这就是数据处理服务的起点。

技术课程是另一条路。我们自己从零开始学了很多东西，边学边用、边用边沉淀，慢慢形成了一套自己的学习路径和方法。后来有人看到我们在做的事，说想跟着学。于是就有了课程。

两条线走到今天，背后共享一个判断：技术只占一小半，一大半是理解对方到底想问什么，再把东西翻译成能回答那个问题的样子。不管是帮研究者搭数据通路，还是教别人我们学过的东西，都是同一件事。
