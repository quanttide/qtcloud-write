# 叙事风格迁移方案

## 场景

主营业务：数据处理服务、技术课程服务。

### 核心困境（迁移的锚点）

创新业务，不好和客户介绍。

这是所有迁移的出发点。原文章的张力和价值来自"创始人面对认知困境的挣扎"，业务的对应物就是这一句。以下所有迁移不替换主题，而是**用同一种叙事动作去处理不同的困境素材**。

### 困境映射

| 原始困境 | 叙事动作 | 业务困境 |
|----------|----------|----------|
| a1: 陷入具体场景，不知道自己在做什么 | 跨界找实验室 → 建模 → 验证 | 创新业务无法用现有分类讲清楚，需要先给自己建模 |
| a2: 抽象使用"认知基础设施"却不理解 | 实践突破让概念落地 | 自己的业务自己最清楚，但讲出去客户听不懂 |
| a3: 羞耻感阻止我接受客户视角 | 对话中被打开 → 重新定义 | 不好意思承认业务还没完全定型，怕显得不专业 |
| a4: 拒绝各种消耗 | 平行例示范拒绝 | 拒绝"标准化"，拒绝"对标竞品"，拒绝"等想清楚了再推" |
| a5: 环境信任下降 | 推演一个社会结构 | 客户被各种"AI/大数据"忽悠过，信任重建的困境 |

### 叙事引擎

不变的是"一个人/团队如何从说不清到说清"的认知推演动作。变的只是素材来源：
- 原始素材来源：创始人的个人经历（打游戏、交友、写小说）
- 业务素材来源：项目交付中的摩擦、客户的原话、团队内部复盘

## 样文

我们自己是搞研究出身的。

那几年做实证研究，最怕的不是模型跑不出来，而是数据根本到不了跑模型那一步。工商数据、专利数据、投融资数据，不同渠道来的，格式不统一。同一个企业在甲库叫"XX有限公 司"，在乙库叫"XX有限公司 "——一个空格，系统不认。花了几天对齐名字，又发现新问题：这家企业去年被收购了，代码要不要变？那个专利转了好几次手，归属期怎么算？这种问题占掉了大量时间。每次想去解决，解决到一半就被新问题打断。

那几年反复踩同样的坑，慢慢磨出了一套自己的处理流程。不是什么精巧的设计，就是踩多了自然知道哪里会出问题。

后来转型做了商业公司，开始对外接项目。发现找来的人，很多也是做研究的——经济学、社会学、公共管理。手上攒了一堆数据，想做正经的分析，但大部分时间卡在数据处理上，真正的研究没怎么动。他们的处境我们太熟悉了。没多想，就把自己当年那套流程拿出来用。

做了几个项目之后发现，真正需要的不是一次性的清洗。因为真正的研究需求一直会变，数据源也会变，所以很快就发现这条路不通。不如改成帮人搭一条从原始素材到可用语料的通路：机器能判断的归机器，需要研究者判断的做成标注流程。这是数据处理服务的起点。

技术课程是另一条路。很多是有人看到我们做的事情，问能不能教。想了下，确实好些东西是从零开始学的——边学边用、边用边沉淀，慢慢就有了一套方法。那就教。

可能是自己学出来的，踩过坑才知道别人会在哪里卡住。所以课程不太讲工具操作，讲的是怎么把一个问题翻译成数据问题，再把数据翻译成能回答那个问题的样子。

两条线走到今天，背后共享一个判断：技术只占一小半，一大半是理解对方到底想问什么，再把东西翻译成能回答那个问题的样子。不管是帮研究者搭数据通路，还是教别人学东西，都一样。

这个判断不是坐在办公室里想出来的。
