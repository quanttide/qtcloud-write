# 叙事风格迁移方案

## 场景

主营业务：数据处理服务、技术课程服务。

### 核心困境（迁移的锚点）

创新业务，不好和客户介绍。

这是所有迁移的出发点。原文章的张力和价值来自"创始人面对认知困境的挣扎"，业务的对应物就是这一句。以下所有迁移不替换主题，而是**用同一种叙事动作去处理不同的困境素材**。

### 困境映射

| 原始困境 | 叙事动作 | 业务困境 |
|----------|----------|----------|
| a1: 陷入具体场景，不知道自己在做什么 | 跨界找实验室 → 建模 → 验证 | 创新业务无法用现有分类讲清楚，需要先给自己建模 |
| a2: 抽象使用"认知基础设施"却不理解 | 实践突破让概念落地 | 自己的业务自己最清楚，但讲出去客户听不懂 |
| a3: 羞耻感阻止我接受客户视角 | 对话中被打开 → 重新定义 | 不好意思承认业务还没完全定型，怕显得不专业 |
| a4: 拒绝各种消耗 | 平行例示范拒绝 | 拒绝"标准化"，拒绝"对标竞品"，拒绝"等想清楚了再推" |
| a5: 环境信任下降 | 推演一个社会结构 | 客户被各种"AI/大数据"忽悠过，信任重建的困境 |

### 叙事引擎

不变的是"一个人/团队如何从说不清到说清"的认知推演动作。变的只是素材来源：
- 原始素材来源：创始人的个人经历（打游戏、交友、写小说）
- 业务素材来源：项目交付中的摩擦、客户的原话、团队内部复盘

## 样文

你手上有一批数据。工商注册的、专利的、投融资的，来自不同渠道，花了不少精力拿到。你打算做一次正经的分析，跑模型、出结论。

然后你卡在了一个预料之外的地方。

同一个企业在这个渠道叫"XX有限公 司"，在另一个渠道叫"XX有限公司 "——一个空格，系统不认。你花了三天对齐名字，接着发现更深的坑：这家企业去年被收购了，代码要不要变？那个专利转了好几次手，归属期怎么算？

你原本想研究的问题一步都没动，时间全花在了"让数据长得像能用的样子"上。

这不是工具问题。换成再贵的软件，空格也不会自己消失；也不是能力问题，你做研究的判断力在清洗环节根本用不上。这是**原始素材到可用语料之间缺了一条通路**。

我们做的就是铺这条路。把"机器能判断的"和"需要研究判断的"拆成两层——前者自动化，后者做成标注流程，让你在一个界面里批量确认。最终交付的不是一堆清洗脚本，是一套按你的研究逻辑组织好的数据资产。

一个客户在论文致谢里写：数据处理本身不是障碍了，终于可以把时间放在想问题上。

所以我们定义了两条业务线：**数据处理服务**帮你把路铺好，**技术课程服务**让你的团队以后自己能铺。两条线共享同一个前提——技术只占一小半，一大半是理解你到底想问什么，再把数据翻译成能回答这个问题的样子。

如果你手上有数据一直想用但还没用起来，可以先找我们交流一下。聊完你的研究对象和数据现状，再判断我们能做什么。
